009                                                 Abstract
010
011              Despite growing interest in AI agents across industry and academia, their exe-
012              cution in an environment is often slow, hampering training, evaluation, and de-
013              ployment. For example, a game of chess between two state-of-the-art agents may
014              take hours. A critical bottleneck is that agent behavior unfolds sequentially: each
015              action requires an API call, and these calls can be time-consuming. Inspired by
016              speculative execution in microprocessors and speculative decoding in LLM infer-
017              ence, we propose speculative actions, a lossless framework for general agentic
018
                 systems that predicts likely actions using faster models, enabling multiple steps
                 to be executed in parallel. We evaluate this framework across three agentic en-
019
                 vironments: gaming, e-commerce, web search, and a “lossy” extension for an
020
                 operating systems environment. In all cases, speculative actions achieve substan-
021              tial accuracy in next-action prediction (up to 55%), translating into significant
022              reductions in end-to-end latency. Moreover, performance can be further improved
023              through stronger guessing models, top-K action prediction, multi-step speculation,
024              and uncertainty-aware optimization, opening a promising path toward deploying
025              low-latency agentic systems in the real world.

      1     Introduction
029
      Large language model (LLM)-driven agents are shifting from single-shot predictions to processes
030
      that run inside rich environments: browsers, operating systems, game engines, e-commerce stacks,
031
      and human workflows. These environments are not incidental; they determine what the agent can
032   observe and do, gate progress through interfaces and rate limits, and dominate end-to-end latency. In
033   practice, the agent’s behavior unfolds as a sequence of environment steps (tool calls, Model Context
034   Protocol (MCP) server requests, human-in-the-loop queries, and further LLM invocations), each
035   with non-trivial round-trip time and cost. As capabilities improve, a new bottleneck emerges: time-
036   to-action in the environment. Even when accuracy is high, an agent that pauses too long between
037   steps is impractical for interactive use or high-throughput automation.

051            Must an agent interact with its environment in a strictly sequential manner?

      predict and tentatively pursue the most likely next actions using faster models, while slower ground-
055   truth executors (powerful LLMs, external tools, or humans) catch up. In effect, the agent stages
056   environment interactions (prefetching data, launching safe parallel calls, and preparing reversible

096   A key design goal is losslessness relative to the environment’s baseline semantics: speculative ac-

101   shopping carts before checkout, and OS-level operations in a sandbox) these patterns are natural and
102
      inexpensive to implement.

122   1.1   Related Work
123
124
      Speculation in microprocessors Speculation emerged in the field of computer architecture to
      increase parallelism by executing instructions before their outcomes were resolved (Tomasulo,
125
      1967), rolling back when predictions were wrong, and became central to high-performance pro-
126
      cessors (Lam & Wilson, 1992). In light of security vulnerabilities that exploit microarchitectural
127   speculative execution, (Mambretti et al., 2019) developed Speculator to analyze CPU speculation
128   behavior.
129
130   Speculative program execution Thread-level speculation executes sequential program fragments
131   in parallel. It assumes that those program fragments are independent and can be safely parallelized,
132   but must roll back and resolve conflicts if it turns out some threads are data dependent (Estebanez
133   et al., 2016). Recently, (Liargkovas et al., 2023) explored the use of tracing and containment to
134   speculatively but safely run shell scripts out of order.
135
136   Speculative decoding in LLM inference The same predict-verify pattern was recently applied to
137
      large language models. Speculative decoding accelerates autoregressive inference by using a small
      draft model to propose tokens that a larger target model verifies in batches, committing correct
138
      ones and regenerating failures (Leviathan et al., 2023; Zhang et al., 2024; Chen et al., 2023). At
139
      the reasoning level, speculation has also been used to accelerate chain-of-thought processes (Wang
140   et al., 2025b;a; Fu et al., 2025). In all cases, speculation reduces latency in sequential pipelines by
141   executing likely future steps in parallel with their validation.
142
143   Other applications of speculations Speculation has been widely applied in a number of systems
144   contexts. For example, Speck (Nightingale et al., 2008) uses it to parallelize otherwise sequential se-
145   curity checks, and AutoBash (Su et al., 2007) uses it to test configuration changes in isolation. More
146   recently, Farias et al. (2024) developed a speculative, GPU-friendly policy simulation technique for
147   optimizing supply chain systems.
148   Motivated by these work, we propose a speculative framework for agentic systems to achieve lossless
149   execution speedups. Our approach is aligned with recent studies that speculate LLM API calls for
150   planning tasks (Hua et al. (2024), Guan et al. (2025)), but generalizes the idea to the entire agentic
151   environment—by not only speculating LLM calls, but also internal and external tool APIs, MCP-
152   server APIs, and even human responses. This yields a unified framework for agentic speculation,
153   particularly consistent with the emerging “environment” and MCP perspectives on agentic systems,
154   providing a powerful mechanism for breaking the bottleneck in the training and deployment of AI
155   agents.

157   2     Framework
158
159   An agentic system is usually modeled as a Markov Decision Process (MDP) (st , at ), where st denotes
160   the state and at the agent’s action at step t. This model admits considerable flexibility: an action may
161   represent a chatbot response, the choice of a tool to invoke, or a button clicked by a computer-use
      agent, among others.

      From a systems perspective, we model each action in an agentic system as an API call, which may
163   block execution until a response is returned. This abstraction offers two key advantages: (1) it
164   precisely defines what constitutes an action, and (2) it provides a unified framework for optimizing
165   system latency, as we will see shortly. Notably, this perspective aligns with the recent development
166   of MCP servers for agentic systems (Anthropic, 2024).
167

181   This formulation subsumes a broad range of realizations:
182
      • LLM calls: each invocation of an LLM within the agent can be treated as an action.
183
184
      • Tool / MCP server calls: each actual call for internal/external tools is treated as an action: e.g.,
        terminal access, web search, deep research APIs, weather APIs, or browser-use MCPs.
185
186   • Human-as-an-API calls: furthermore, human responses themselves can be abstracted as API
187
        calls, often incurring even longer latencies than automated tools.
188   Given this abstraction, the fundamental bottleneck in executing agentic systems becomes apparent:
189   each API call must complete before the next can be issued. To break this sequential dependency,
190   we propose to speculate a set of API responses {ât } using a faster model while waiting for the true
191   response at . This enables speculative API calls for step t + 1 to be launched in parallel. At time t, if
192   the API call (ht , qt ) can be found in the cache (cache hit), the system can skip the actual invocation
193   and only wait for the pending action corresponding to this call to return (if not already returned).
194   Formally, the algorithm is specified in Algorithm 1.
195   The resulting speedup relies on two key assumptions:
196
      Assumption 1 (Speculation accuracy). The speculative model ĝ can guess the current-step response
197   at accurately enough that the implied next call (ht+1 , qt+1 ) = π( f (st , ât )) matches the true next call
198   with non-zero probability p > 0.
199
200   As shown later, this often holds in practice because API responses are typically predictable.
201   Assumption 2 (Concurrent, reversible pre-launch). Multiple API calls can be launched concur-
202   rently, and pre-launched calls that do not correspond to the realized trajectory have no externally
203   visible side effects (or can be rolled back).
204
      In practice, this assumption is satisfied under modest traffic for many external APIs (e.g., web search,
205
      OpenAI LLM queries, email lookups). For self-hosted LLMs, concurrent calls also incur only
206   minimal additional cost due to continuous batching.

244   Extension. Algorithm 1 is only a simple demonstration of the speculative action idea. For example,
245   one can naturally extend Algorithm 1 to multi-step speculation, where the Speculator predicts not

      only the next step but up to s steps ahead. This yields a tree-search structure with deeper rollouts.

247
      uniformly, the Speculator also estimates confidence for each guess (e.g., via prompting LLMs or
248
      uncertainty-quantification methods). The most promising branches can then be expanded in a beam-

250   leave for future deeper investigation. Despite Algorithm 1’s simplicity, the results from the four use

253

254
      not the focus of this work, we provide an analysis of our experiments in Appendix B. For self-hosted
255   LLMs, this increased cost is largely mitigated through batching.
256
257   Side effects and safety. Speculation executes a hypothesized next action ât+1 that may be wrong, so
258
      safety requires the ability to simulate first and then commit or roll back. In domains like chess, roll-
      back is trivial; in others, overwrite is easy (e.g., OS tuning). But many systems involve irreversible
259
      or externally visible effects (e.g., deleting records, placing orders), where naive speculation is harm-
260
      ful. Thus, speculation must be limited to cases where mispredictions are reversible, via forking,
261   snapshot restoration, or roll-forward repair (e.g., refund/replace).

325
326   We evaluate our framework in terms of both time saved and prediction accuracy.
327   We track two metrics: (i) prediction accuracy, defined as the fraction of rounds in which any specu-
328   lative prediction matches the actual move, and (ii) time saved, computed as (T seq − T s )/T seq , where
329   T s and T seq denote speculative and sequential execution times, respectively.
330
      Time Saved and Accuracy increases with more predictions. Figure 2 reports results over 30

      steps. Our framework consistently reduces execution time compared to sequential play, with larger
332   savings as the number of speculative predictions increases. Across 5 runs, using 3 predictions yields
333   an average time saving of 19.5% with an average prediction accuracy of 54.7%.
334
335
      Randomness of agent call in game-play Variance in Figure 2 reflects realistic game-play dynamics

336
      the resulting position admits an obvious response, little acceleration occurs, as computation would

341   3.2     E-Commerce Environment
342   Beyond competitive game-play, customer-agent interactions in the e-commerce provide a real-world
343   setting where speculative actions can substantially improve performance. In a typical workflow, the
344   customer submits a query through a chat interface and waits for the agent to respond. When the
345   agent needs to invoke multiple API calls sequentially—for example, processing a return may in-
346   volve retrieving order information, validating eligibility for each item, and initiating the return—the
347   resulting latency can significantly degrade user experience. By contrast, if some API calls are cor-
348   rectly speculated and executed in advance, the agent can return results immediately once the query
349   arrives, greatly reducing latency and making the interaction feel seamless. We evaluate this setting
350
      using the retail environment from τ-bench Yao et al. (2024).

456   4     Beyond Lossless Speculation: OS Hyperparameter Tuning Environment
457
      Thus far, our experiments have focused on lossless speculation, where speculative actions are vali-
458
      dated sequentially before commitment. We now turn to a lossy setting that relaxes this step-by-step
459
      constraint. In latency-sensitive environments like an operating system, waiting for a powerful but
460   slow Actor (10-15s deliberation) can leave the system in a degraded state. Our framework uses a
461   fast Speculator to apply immediate adjustments, improving real-time performance, while the Actor
462   deliberates. This is made safe by a last-write-wins mechanism—the Actor’s final decision simply
463   overwrites any speculative action, removing the need for complex rollbacks. This method acceler-
464   ates convergence and improves reaction time, which we evaluate on the sysbench cpu benchmark,
465   a CPU-bound workload (Kopytov, 2020).
466
467   4.1   Experimental Setup
468   We tune a single parameter of Linux’s Completely Fair Scheduler (CFS), min granularity,
469   which controls a task’s minimum timeslice. This knob strongly affects scheduling performance:
470   smaller timeslices reduce latency but can degrade throughput, yielding a classic trade-off. Prior
471   work (Liargkovas et al., 2025) demonstrated that an LLM-based agent can optimize this parameter;
472   here, we extend that setup with a speculative control loop.
473   Our system consists of a fast Speculator and a slow Actor. The Speculator proposes a bounded pa-
474   rameter update each second using the latest performance metric. The Actor, in contrast, responds
475   every 10–15 seconds after analyzing a compressed chronology of the Speculator’s recent (measure-
476   ment, action) pairs. When the Actor’s response arrives, its chosen setting is immediately applied and
477   its state updates the Speculator’s context, ensuring subsequent fast steps proceed from a validated
478   narrative rather than drifting.
479   Evaluation    We evaluate three systems:
480
481   1. Actor-only: slow but deliberative (10–15 s interval);
482   2. Speculator-only: fast (1 s interval) but non-extensive;
483
484   3. Speculator–Actor: combined system using speculative updates between Actor decisions.
485   We are interested in (i) reaction time, (ii) convergence speed to the optimal setting, and (iii) ability
      to avoid local minima that trap the Speculator-only baseline.

523     5                      Conclusion
524
525
        In this paper we propose Speculative Actions, a lossless framework for accelerating general agen-
        tic environments by breaking the strict sequentiality of their interaction loops. Unlike specula-
526
        tive decoding in LLM inference, our approach generalizes speculation to the full spectrum of
527
        agent–environment interactions, treating every step, whether an LLM call, tool invocation, MCP
528     request, or human response, as an API call subject to prediction and parallelization. By pairing a
529     fast Speculator with a slower but authoritative Actor, the framework enables agents to anticipate
530     and prepare likely next actions in parallel, transforming otherwise idle waiting time into productive
531     computation. We formally analyze the expected speedup and instantiate the framework across four
532     representative environments. Empirically, we observe substantial latency reduction in all of them.
533     Notably, while most environments adopt a strictly lossless validation process, our OS hyperparame-
534     ter experiment demonstrates that relaxing this constraint enables fast exploratory updates, extending
535     speculation to adaptive control scenarios.
536     More broadly, speculative actions reveal a systems-level design principle for modern agents: par-
537     allelism in environment interactions. Future work could extend this idea through multi-step and
538     uncertainty-aware speculation, tighter integration with reinforcement learning and environment sim-
539     ulators. Together, these directions point toward general-purpose, real-time agentic systems where
        speculation becomes a first-class mechanism for efficient decision making.

1140   C.3   Heuristic Policy for Confidence-Aware Speculation
1141
1142   The breadth-focused strategy analyzed above assumes that all speculative branches share the same
1143   accuracy p. In practice, however, modern agentic systems often have access to per-branch confi-
1144   dence estimates. Such confidence signals can arise from a variety of sources:
1145
1146
             • intrinsic model scores (e.g., logits or calibrated probabilities),
1147         • prompting the model to output a confidence alongside each speculative prediction,
1148         • or a separate auxiliary predictor trained to estimate speculation correctness.
1149
1150   Whenever such per-branch confidence information is available, the system need not treat all specu-
1151   lative branches uniformly. Instead, it can make selective speculation decisions, accepting only those
1152   branches whose predicted correctness justifies the additional latency and cost.
1153

1262
               • If speculation is generally unreliable (small p), then p⋆ increases: only high-confidence
1263             branches are worth accepting.
1264
               • The resulting policy is lightweight: the system compares a single observed value pi to a
1265
                 precomputed global threshold p⋆ .
1266
1267   In summary, whenever per-branch correctness confidence is available—regardless of how that confi-
1268   dence is obtained—a simple threshold rule emerges as an effective and interpretable online decision
1269   rule for balancing cost and latency.

       C.4     Depth focused search
1278
1279   In the most general setting, a policy may choose both (i) how many parallel speculative branches
1280   to launch, and (ii) how “deep” to unroll each speculative branch before initiating a real API call.
1281   Analyzing the optimal policy in this full space is highly non-trivial due to the branching structure of
1282   the execution tree.
1283   To build intuition, we analyze two extrema regimes: (1) a breadth-focused regime, where at each
1284   step we launch k parallel speculations and immediately follow each with an API call, and (2) a
1285   depth-focused regime, where execution follows a single branch as far as speculation and real API
1286   calls allow.
1287
       These two settings correspond to simplified extremes of the decision space, providing interpretable
1288
       analytic characterizations of the cost–latency tradeoff.
1289
1290   We analyzed the first in the previous section, and now analyze the opposite extreme: a depth-
1291   focused strategy. Under this policy, whenever either a speculative or real API call returns, the system
1292
       launches one new real call and one speculation on top of that branch. If the real API result is incon-
       sistent with the corresponding speculative guess, all descendants of that speculation are discarded.
1293
