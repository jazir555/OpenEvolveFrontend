# ADR-005: Anti-Corruption Layer (ACL) Implementation

## Status
**Accepted**

## Context
The OpenEvolve Frontend integrates 30+ external services with conflicting conventions:
- **Field naming**: camelCase vs snake_case vs PascalCase
- **Date formats**: ISO strings vs Unix timestamps vs Date objects
- **Error formats**: HTTP status codes vs error objects vs string messages
- **Pagination**: page/offset vs cursor-based

**The Problem**: Without protection, external "messiness" infects our clean internal code.

## Decision
Implement **Anti-Corruption Layer (ACL)** at adapter boundaries.

### Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                      OpenEvolve Core                        │
│                  (Clean, consistent)                         │
└─────────────────────────────────────────────────────────────┘
                            ▲
                            │
                    ┌───────┴────────┐
                    │  Event Bus    │
                    │  (Canonical)   │
                    └───────┬────────┘
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
┌───────┴────────┐  ┌───────┴────────┐  ┌──────┴─────────┐
│ Adapter A      │  │ Adapter B      │  │ Adapter C      │
│ (Normalize)    │  │ (Normalize)    │  │ (Normalize)    │
└───────┬────────┘  └───────┬────────┘  └──────┬─────────┘
        │                   │                   │
┌───────┴────────┐  ┌───────┴────────┐  ┌──────┴─────────┐
│ Service A      │  │ Service B      │  │ Service C      │
│ (Messy)        │  │ (Messy)        │  │ (Messy)        │
└────────────────┘  └────────────────┘  └────────────────┘
```

### Implementation

#### Adapter Responsibilities
Each adapter MUST:
1. **Accept** external service format
2. **Validate** data using Zod schemas
3. **Transform** to canonical format
4. **Emit** canonical events
5. **Never** let external format leak into core

#### Transformation Layer
```typescript
// Example: RAGBits Adapter

// External format (messy)
interface RAGBitsSearchResponse {
  results: Array<{
    doc_id: string;        // snake_case
    score_val: number;     // weird naming
    meta: any;             // untyped
  }>;
  total_count: number;
}

// Canonical format (clean)
interface CanonicalSearchResult {
  id: string;
  score: number;
  metadata: Record<string, unknown>;
  timestamp: string;
}

// Adapter: Transform external → canonical
function normalizeRAGBitsResponse(
  external: RAGBitsSearchResponse
): CanonicalSearchResult[] {
  return external.results.map(r => ({
    id: r.doc_id,
    score: r.score_val,
    metadata: r.meta || {},
    timestamp: new Date().toISOString()
  }));
}
```

#### Event Bus Integration
- All events on event bus use canonical format
- Adapters emit canonical events
- Core code only consumes canonical events

### Benefits
1. **Isolation**: External changes don't break core code
2. **Consistency**: Core code sees uniform data
3. **Testing**: Easy to mock canonical data
4. **Flexibility**: Can swap backend without changing core

## Consequences

### Positive
- ✅ **Isolation**: Protected from external changes
- ✅ **Consistency**: Uniform data everywhere
- ✅ **Testability**: Easy to create test data
- ✅ **Flexibility**: Can replace services easily

### Negative
- ⚠️ **Boilerplate**: Need transformation code
- ⚠️ **Performance**: Small overhead from conversion
- ⚠️ **Maintenance**: Transformations need updates

### Mitigations
- Keep transformations simple and pure
- Use type-safe conversion (Zod)
- Write tests for all transformations
- Document external format requirements

## Alternatives Considered

### Alternative 1: Direct Integration
**Description**: Use external formats directly in core code

**Pros**: Less boilerplate, faster

**Cons**: Tight coupling, fragile to changes

**Rejected**: Violates isolation requirements

### Alternative 2: Shared Types
**Description**: Use same types as external services

**Pros**: No conversion

**Cons**: Inconsistent conventions, conflicts

**Rejected**: Doesn't solve the problem

### Alternative 3: Universal Adapter
**Description**: One adapter for all services

**Pros**: Single place for logic

**Cons**: Complex, hard to maintain, brittle

**Rejected**: Doesn't scale to 30+ services
